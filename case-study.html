RISC vs. CISC • Choosing a Processor

Computer Organization and Architecture (25CST-238) • Shriya, Roll No. 25BAI10016 • B.Tech CSE (AI), Chandigarh University

Scenario

A technology company develops two computing systems: one uses a RISC architecture and the other uses a CISC architecture. The team must select a suitable instruction-set design for a low-power embedded device.

Problem Statement

Compare the two processor architectures and justify the preferred option for a given use case.

The use case here is a battery-powered embedded device, such as a sensor node, a wearable or a small controller. For a device like this, energy per instruction, chip size and cost, and predictable timing matter more than raw performance. This case study looks at both architectures with those priorities in mind.

Low power Small chip area Predictable timing Low cost

Case Study Questions

RISC (Reduced Instruction Set Computer) uses a small set of simple, uniform instructions, and most of them complete in about one clock cycle. Only LOAD and STORE instructions access memory; all other work happens between registers. RISC chips usually have many registers and a simple, often hardwired, control unit. Examples: ARM, RISC-V, MIPS.

CISC (Complex Instruction Set Computer) provides a large set of instructions, and some of them perform several steps at once, such as reading from memory, calculating and writing back in a single instruction. These instructions have different lengths and take a variable number of cycles, and the control unit is often microprogrammed. Examples: Intel x86, VAX, Motorola 68000.

In short: RISC keeps the hardware simple and leaves the optimisation work to the compiler. CISC puts more work into the hardware so that programs can be shorter.

When every instruction has the same size (32 bits in MIPS, RISC-V and classic ARM), the processor knows where the next instruction starts without looking at the current one. This gives several benefits:

  • Simple fetch: the program counter just moves forward by a fixed step (for example, +4 bytes).
  • Simple, fast decoding: the opcode and register fields are always in the same bit positions, so the decoder only has to read them.
  • Smooth pipelining: the pipeline can fetch the next instruction while the current one is still being decoded, because nothing needs to be worked out first.
  • Memory alignment: instructions line up neatly with words in memory and cache lines.

Drawback: programs get somewhat larger, because even a simple operation takes the full instruction width. To reduce this, some designs add short 16-bit forms (ARM Thumb-2 and the RISC-V "C" extension) while keeping decoding easy.

The more varied and complex the instructions are, the harder the decoder has to work.

Complex (CISC) case: an x86 instruction can be anywhere from 1 to 15 bytes long. It may carry prefixes, an optional addressing byte, a displacement and an immediate value. The decoder has to read part of the instruction to find its length before it can even locate the next one. Some instructions are so complex that they are handled by microcode. All this needs more logic, more transistors and more power, and it makes it hard to decode several instructions in parallel.

Simple (RISC) case: decoding is mostly reading fixed bit fields: opcode, source register, destination register, immediate. This is fast, cheap and low in power. The chip area saved can be used for more registers or cache.

Note: modern x86 processors hide this cost by translating complex instructions into simple internal micro-operations. That works well for performance, but the translation hardware itself uses area and energy, which is a disadvantage for battery-powered devices.

RISC approach: only a few simple modes are provided, typically register, immediate and base register + offset. Only load/store instructions touch memory, so arithmetic instructions work purely on registers. This keeps the hardware simple and every instruction predictable.

CISC approach: many modes are provided, such as direct, indirect, indexed, base + index × scale + displacement, and in some machines even memory-to-memory operations. Most instructions are allowed to use these modes, so one instruction can fetch operands from memory, compute and store the result.

Yes, it can, and the reason is code density.

One CISC instruction can do the work of several RISC instructions, so the same program takes up fewer bytes. A smaller program means fewer instruction fetches from memory and better use of a small instruction cache. When memory is slow or the cache is limited, fetching fewer bytes can make the CISC machine finish sooner, even if each instruction is individually more complex.

Extra point: modern x86 chips also convert complex instructions into RISC-like micro-operations inside, so they get the benefits of both styles. This is why performance depends on the whole design (pipeline, cache, clock speed), not only on whether the instruction set is RISC or CISC.

(b) Example Instruction Sequences

Example 1: counter = counter + 1

A variable stored in memory is incremented by one.

CISC (x86) — 1 instruction

ADD  DWORD PTR [counter], 1   ; read memory, add 1, write back

RISC (ARM) — 3 instructions

LDR  R1, [R0]      ; load counter (R0 = its address)
ADD  R1, R1, #1    ; add 1 in a register
STR  R1, [R0]      ; store the result back

Observation: the CISC version is shorter, but it hides three steps inside one instruction with a variable cycle count. The RISC version needs more instructions, but each one has a fixed size, takes about one cycle and moves smoothly through the pipeline.

Example 2: Copying a block of N bytes

Data is copied from a source area to a destination area.

CISC (x86) — 1 instruction

; ESI = source, EDI = destination, ECX = N
REP MOVSB    ; repeat: copy a byte, advance pointers, ECX = ECX - 1

RISC (ARM) — a short loop of 4 instructions

; R0 = source, R1 = destination, R3 = N
loop: LDRB R2, [R0], #1   ; load a byte, then move source pointer
      STRB R2, [R1], #1   ; store the byte, then move destination pointer
      SUBS R3, R3, #1     ; decrement count and set flags
      BNE  loop           ; repeat until count is zero

Observation: CISC wins on code size (one instruction against four). RISC gives simple, predictable steps that are easy to pipeline and to time exactly.

(c) Processor Recommendation — battery-powered embedded device

Recommended: a RISC processor, such as an ARM Cortex-M or a RISC-V microcontroller.

  1. Lower power consumption. A simple decoder and fixed-length instructions mean fewer transistors switching for every instruction, so less energy is drawn from the battery. This is the most important factor for a battery-powered device.
  2. Smaller, cheaper chip. Less control logic gives a smaller die, lower manufacturing cost and less heat, so no fan or heat sink is needed in a compact device.
  3. Predictable timing. Embedded tasks such as sensor reading or motor control often have real-time deadlines. Mostly single-cycle instructions make execution time easy to calculate.
  4. Efficient pipelining at a low clock speed. Uniform instructions keep the pipeline busy, so useful work gets done without a high clock rate. A lower clock saves further power.
  5. Mature ecosystem. ARM and RISC-V have wide compiler, library and microcontroller support, including deep sleep modes made for battery life.

Trade-off and how to reduce it: RISC programs are larger and need more instruction fetches. Flash memory is cheap, and compressed instruction sets (ARM Thumb-2 and the RISC-V "C" extension) recover most of the gap. CISC advantages such as raw speed on complex workloads matter little for a device whose main goal is a long battery life.

Conclusion: CISC tries to do more per instruction, while RISC tries to do each instruction cheaply and quickly. For a low-power, battery-powered embedded device, the simplicity, efficiency and predictability of RISC make it the better choice.
